# 6.1 会话管理生命周期与数据结构

在第一和第二部分中，我们打通了智能体（Agent）的决策死循环与工具执行链路。然而，大模型本身依然是无状态的（Stateless）。要让智能体在经历漫长的时间线、多次网络重启，甚至服务器断电后，依然能连贯地承接上文的语境并继续工作，底座必须建立起一套高内聚的**会话（Session）与状态维护机制**。

对智能体而言，会话不是简单的“聊天历史文本备份”，而是它大脑的**心流状态寄存器**。

本节我们将详细拆解会话在底座中的物理生命周期，解剖 Session 的核心状态字段，并针对海量多会话长期运行环境下极易触发的“内存泄露与 OOM 崩溃”大坑提供架构级的防御策略。

---

## 一、 记忆是智能体“心流”的物理载体

如果把 ReAct 执行器比作智能体的“CPU”，那么 Session 会话就是它的“内存条”和“高速缓存”。

智能体的会话管理之所以比普通 Web 应用的 Session 复杂得多，是因为它不仅要保存“历史对话文本”，还要实时跟踪和更新智能体当前的**心智与物理状态空间**。这包括：
*   **当前激活的技能卡（Active Skill ID）**：智能体当前正处于什么专业的工作模式中？
*   **当前激活的工具箱（Active Toolbox IDs）**：大模型当前有权支配哪套工具资源？
*   **工具箱闲置轮数（Toolbox Idle Rounds）**：哪些工具箱正处于闲置状态，需要底座主动进行垃圾回收？
*   **当前绑定的基模型（Model ID）**：本次对话大模型降级链当前落在了哪一家提供商的哪一个模型上？

所有这些非文本的结构化状态，共同缝合出了智能体在进程运行时层面的**“心流（Context Flow）”**。

---

## 二、 会话（Session）的物理生命周期

在 Freya 底座的设计中，会话在物理上经历四个核心生命周期阶段：

```
 [创建 (Birth)] ──> 分配 Session ID，载入默认模型与工具箱
       │
       ▼
 [流转与追加 (Ingestion)] ──> 每轮 ReAct 往返更新内存缓存，写透落盘
       │
       ▼
 [压缩与重组 (Compacting)] ──> 逼近 Token 额度上限，调用 LLM 摘要归档
       │
       ▼
 [冷冻与消亡 (GC / Death)] ──> 长期闲置，内存自动淘汰释放，只留磁盘物理文件
```

### 1. 创建（Birth）
当用户通过 Telegram 或 CLI 连入智能体，底座首先会为其分配一个全局唯一的 `sessionId`。
执行器会为其初始化一个空白的状态结构，注入默认的模型路由配置、默认元工具箱（`meta`），并写入物理磁盘。

### 2. 流转与追加（Ingestion & Update）
在 `while(loop)` 决策死循环中，每一次大模型输出 Tool Call 或是执行完工具得到 Observation，执行器都会调用 `SessionManager.appendMessage()` 往历史列表里追加数据。
为了防止系统宕机导致记忆丢失，每一次内存中的追加，底座都**必须执行“写透（Write-Through）”策略** —— 实时同步写入磁盘的持久化文件中。

### 3. 压缩与重组（Compacting & Archive）
当多轮对话的 Token 消耗逼近大模型的最大窗口（Context Window）时，底座会主动切断正常循环，启动 `SessionCompactor`，将陈旧的对话记录编译为“摘要记忆（Summary）”，替换原本琐碎的 messages。

### 4. 冷冻与消亡（GC / Death）
在长期运行环境中，数以千计的会话如果一直将完整消息列表常驻在服务器的内存 Map 中，会迅速耗尽 Node.js 的堆显存。因此，当会话处于非活跃状态时，底座通过索引分离机制**只保留轻量索引在内存中**，完整消息历史只留存在磁盘上的物理文件。当下一次该会话被唤醒交互时，底座再从磁盘按需延迟加载。

## 三、 Session 数据结构的物理定义

在 Freya 底座中（位于 `packages/core/src/session/types.ts`），会话采用**“轻量索引与完整实体分层”**的设计：

```typescript
// 1. 存入 sessions.json 的全局轻量索引条目
export interface SessionIndex {
  id: string;                                // 会话业务标识（如 'main'）
  uuid: string;                              // 物理存储唯一 UUID
  parentId: string | null;                   // 父会话指针（支持子智能体分支）
  archived: boolean;                         // 是否已归档
  archivedAt: string | null;                 // 归档时间戳
  summary?: string;                          // 压缩后的长期记忆摘要
  updatedAt: string;                         // ISO 8601 最后更新时间
  modelId?: string;                          // 当前绑定的模型 ID
  providerId?: string;                       // 当前绑定的提供商 ID
  activeSkillId?: string;                    // 当前激活的技能卡
  activeToolboxIds?: string[];               // 当前激活授权的工具箱列表
  toolboxIdleRounds?: Record<string, number>;// 工具箱闲置迭代计数器
  // Token 与计费统计
  promptTokens?: number;
  completionTokens?: number;
  totalTokens?: number;
  cost?: number;
}

// 2. 内存中的完整会话对象（继承轻量索引，挂载历史消息实体）
export interface Session extends SessionIndex {
  history: LLMMessage[];                     // 完整的对话消息列表
  lastSnapshotId: string | null;             // 最新压缩快照文件 ID
}
```

## 四、 【架构防线】海量多会话下的内存防爆设计：轻重双层索引与懒加载

很多新手开发者在设计智能体会话系统时，习惯将所有会话的完整对话历史全部常驻在全局 Map 中。

### 1. 内存泄露与 OOM 隐患
大模型的 Message 历史列表由于包含了大量 raw JSON、图片 Base64 附件和庞大的工具返回文本，**单个 Session 的内存占用可能高达数兆至数十兆字节**。
在长期运行或频繁创建分支会话的场景下，如果有数千个历史会话积累，常驻内存的体积会以惊人的速度膨胀，极易突破 Node.js 默认 1.4 GB 的堆内存上限，引发 **OutOfMemory (OOM) 崩溃**。

### 2. Freya 的物理防爆防线：双层索引与按需懒加载（Lazy-Loading）
为了彻底规避 OOM，Freya 在 `SessionManager` 与 `persistence.ts` 中设计了**“轻重分离的双层索引”**架构：

*   **轻量全局索引常驻（`sessions.json`）**：
    系统启动时，`persistence.loadIndex()` 仅将几百字节的 `SessionIndex` 载入内存中的 `sessionIndices` Map。即使存在 100,000 个历史会话，内存开销也仅有几兆字节。
*   **消息体按需懒加载（`lazyLoadSession`）**：
    只有当某个特定会话收到用户消息或需要与 LLM 交互时，底座才通过 `lazyLoadSession(id)` 从 `~/.freya/data/sessions/<uuid>/session.json` 中异步读取 `history` 消息体并反序列化载入内存。
*   **消息压缩快照外置（`<snapId>.json`）**：
    当活跃会话发生上下文压缩时，被裁剪掉的历史消息会被存盘为独立的快照文件，不阻塞主会话文件与内存体积。

```typescript
// 摘自 packages/core/src/session/session-manager.ts
private async lazyLoadSession(id: string): Promise<Session> {
  // 1. 如果内存已有且未归档，极速返回缓存
  const cached = this.sessions.get(id);
  if (cached && !cached.archived) return cached;

  // 2. 从轻量索引中检索元数据
  const idx = this.findLatestIndexById(id);
  if (!idx) throw new Error(`会话不存在: ${id}`);

  // 3. 仅在命中调用时，从磁盘物理文件按需反序列化完整消息历史
  const data = await this.persistence.loadSessionData(idx.uuid);
  const session: Session = {
    ...idx,
    history: data.history,
    lastSnapshotId: data.lastSnapshotId
  };
  this.sessions.set(id, session);
  return session;
}
```

通过这一层双层索引与按需懒加载屏障，智能体底座的内存开销与总历史会话量彻底解耦，无论历史沉淀了多少会话，系统都能始终平稳运行。

本节我们解剖了智能体会话的物理生命周期、核心状态字段与双层索引懒加载内存防爆设计。在下一小节中，我们将重点分析“数据与源码的物理隔离架构”，看懂 Freya 到底是如何在操作系统底层安全划定边界的。
