# 7.4 调试与避坑指南：递归摘要“套娃死锁”防御

在前几节中，我们研究了滑动窗口与递归摘要的利弊，并白盒剖析了 `SessionCompactor` 的安全回溯截断与 Token 正则预估算法。

在真实的智能体长对话业务中，递归摘要虽然优雅地维护了智能体大脑的“长线记忆”，但它在极端物理边界下，会诱发一个让系统架构师彻夜难眠的**“套娃式”上下文压缩死锁（Summarization Loop Deadlock）**：
*   对话总量超标，底座拦截并调用大模型进行提炼归档。
*   提炼生成的新摘要由于大模型“多嘴”字数偏多，再加上必须保留的活跃消息，重算后的 Token **依然在安全线以上**。
*   底座在下一微秒以为还没有压缩成功，**再次触发压缩调用**...
*   智能体陷入“自己给自己写摘要”的无尽虚空死循环中，API 账单疯狂空转，直至被大厂网关彻底封号拉黑。

本节我们将实际在本地复现这一“套娃死锁”，并设计多重物理防御防线，保护智能体大脑永不宕机。

---

## 一、 递归摘要“套娃死锁”的触发物理过程

大模型的摘要提炼也是一种自回归生成。如果底座对摘要生成的最大 Token 限制不够严格，或者保留的活跃轮数（`keepRecentTurns`）太长，就会在临界点引爆死锁：

```
[Token 消耗 > 85%] ──> 触发前置压缩 ──> 生成 500 Token 的摘要文本
                             │
                             ▼ (重算上下文 Token)
[Token 消耗仍 > 85%] <── 判定依然超限 ──> 再次触发压缩 ──> 生成 600 Token 的摘要文本 (套娃死循环！)
```

在这个死循环中，智能体完全丧失了对用户正常提问的响应能力，网络 I/O 陷入狂暴的空转，是危害性极高的“拒绝服务（DoS）”隐患。

## 二、 本地调试：复现“套娃死锁”

我们在本地模拟一个极小上下文窗口（如 1000 Token 限额）下的记忆提炼过程，并故意使摘要长度膨胀，以复现死锁：

### 1. 套娃死锁复现脚本 (deadlock_test.js)
```javascript
const CONTEXT_LIMIT = 1000;
const WATERMARK = 800; // 80% 水位线

// 模拟的会话历史
let sessionHistory = [
  { role: "user", content: "A".repeat(500) }, // 500 Token 消息
  { role: "assistant", content: "B".repeat(200) } // 200 Token 消息
];

let summary = "";

// 模拟的大模型摘要提炼函数 (因逻辑发散，生成的摘要太冗长)
async function mockLlmSummarize(historyText, prevSummary) {
  console.log("🤖 [LLM 提炼中...]");
  // 故意返回一个高达 450 Token 的冗长摘要，夹杂大量废话
  return "Detailed_Summary_Text_With_Garbage_Characters_" + "X".repeat(400);
}

// 模拟底座的前置同步压缩自检函数
async function compressCheck() {
  let loops = 0;
  
  while (true) {
    loops++;
    const currentTokens = sessionHistory.reduce((sum, m) => sum + m.content.length, 0) + summary.length;
    console.log(`\n--- 检查第 ${loops} 轮 | 当前预估 Token 消耗: ${currentTokens}/${CONTEXT_LIMIT} ---`);

    if (currentTokens <= WATERMARK) {
      console.log("✅ 处于安全水位线以下，允许向用户返回响应。");
      break;
    }

    console.log(`⚠️ 水位超限 (当前 ${currentTokens} > 安全线 ${WATERMARK})，触发前置同步压缩！`);
    
    // 模拟裁剪掉前一半老消息，生成摘要
    const oldHistory = sessionHistory.splice(0, 1);
    const historyText = oldHistory[0].content;

    // 💡 异步生成摘要并注入
    const newSummary = await mockLlmSummarize(historyText, summary);
    summary = newSummary;

    // 重新将摘要包裹为一条系统回顾塞回历史头部
    sessionHistory.unshift({
      role: "user",
      content: `[此前对话摘要回顾]: ${summary}`
    });

    if (loops > 5) {
      console.error("🚨🚨🚨 [套娃死锁确证] 压缩陷入死循环！智能体大脑已彻底瘫痪。");
      process.exit(1);
    }
  }
}

compressCheck();
```

### 2. 测试输出分析
运行此脚本后，你会眼睁睁看着控制台在两轮迭代后，Token 不减反增，迅速陷入了无限次触发 `⚠️ 水位超限，触发前置同步压缩` 的死锁怪圈，直奔崩溃而去。

## 三、 现存源码防线：单次确定性判定与异常截断兜底

为了从根源上彻底斩断死锁链条，Freya 在 `SessionCompactor`（位于 `packages/core/src/session/compactor.ts`）中建立了严密的**“单次确定性执行 + 异常降级滑动截断”**架构防线：

### 1. 架构根源绝杀：消除 `while` 压缩循环
在真实的 `compactor.ts` 中，`compressIfNeeded` 采用单次无循环判定。每一次消息追加仅触发一次水位检测与处理，绝不在局部开启任何 `while` 式反复摘要循环，从架构设计根源上消除死循环的土壤。

### 2. 异常自动降级滑动截断 (Fallback Truncation)
如果大模型在生成摘要时发生异常、超时，或者生成的摘要文本为空：
底座会在 `catch` 块中**自动放弃摘要，无条件降级为滑动窗口截断模式** —— 调用 `findSafeTruncateIndex` 与 `truncateHistory` 直接裁剪历史，确保系统 100% 存活，不阻塞主流程向大模型发包。

```typescript
// 摘自 packages/core/src/session/compactor.ts
try {
  const historyToCompress = history.slice(0, safeTruncateIndex);
  const newSummary = await this.executeSummarize(session, historyToCompress, currentSummary);

  if (!newSummary || newSummary.trim() === '') {
    this.logger?.warn(`[SessionCompactor] 前置压缩生成的摘要为空，放弃应用。`);
    return { type: 'none' };
  }

  // 正常生成快照并打标塞入历史头部
  const snapFile = this.buildSnapshot(session, newSummary, historyToCompress);
  ...
} catch (err: any) {
  this.logger?.error('[SessionCompactor] 触发对话历史压缩管理失败:', err);
  try {
    // 💡 核心安全防线：摘要异常时，无条件触发兜底滑动窗口截断
    const keepTurns = cmConfig.keepRecentTurns || 6;
    const safeTruncateIndex = findSafeTruncateIndex(history, keepTurns);
    if (safeTruncateIndex > 0) {
      this.logger?.warn(`[SessionCompactor] 摘要生成失败，执行兜底滑动窗口截断`);
      this.truncateHistory(history, safeTruncateIndex);
      return { type: 'truncated' };
    }
  } catch (fallbackErr: any) {
    this.logger?.error('[SessionCompactor] 兜底滑动窗口截断也失败:', fallbackErr);
  }
  return { type: 'none' };
}
```

## 四、 避坑经验：设置摘要大雪崩的 Token 边界保护

除了上述两道机制性防线，还有三个细微的物理参数限制，从根源上防范了摘要失控：

1.  **summaryMaxTokens 限制**：在调用 LLM 进行摘要时，底座在模型参数中强行指定 `maxTokens: 150`。利用推理引擎底座的输出 Token 限制从物理上掐断大模型的输出长度，逼迫其精炼，防止摘要文本体积膨胀。
2.  **增量融合与去重**：当历史摘要被带入下一次摘要计算时，Prompt 中明确要求“如果当前已经存在先前的背景提要，请将新内容增量融合成一段连贯的新提要”，避免重复陈述。
3.  **快照独立存盘备份**：在裁剪历史前，底座先调用 `persistence.saveSnapshot` 将被裁剪掉的完整消息存入 `~/.freya/data/sessions/<uuid>/<snapId>.json` 独立物理快照文件。这为后续历史回溯提供了物理备份，即便滑动截断丢弃了老消息，原始对话依然完好保存在磁盘快照中。

通过本节的单次确定性防线、滑动截断降级兜底与快照备份学习，我们彻底攻克了智能体短期记忆系统中最核心的上下文溢出死锁 Bug。
