# 7.3 【白盒剖析】Compactor 与淘汰算法

在 7.2 节中，我们对比了滑动窗口淘汰与递归摘要在拯救上下文溢出危机时的原理与权衡。本节我们将实际切入 Freya 的记忆压缩器核心模块（位于 `packages/core/src/session/compactor.ts`）的 TypeScript 源码。

我们将白盒解剖它是如何通过**双轨压缩判定**实现性能与安全的平衡、如何通过**安全截断点回溯算法（Safe Truncate Index）**物理防御 Tool Call 消息因果断层，以及如何实现**轻量级正则 Token 预估器**以节省 CPU 算力的。

---

## 一、 双轨压缩判定机制：前置防爆 vs 后置静默

在 `SessionCompactor` 中，记忆压缩不是单一触发的，而是分为**前置同步强拦截**和**后置异步静默整理**双轨运行。

### 1. 前置安全强拦截 `compressIfNeeded()`
*   **触发水位**：默认高达 `preCompressThreshold: 0.85`（已使用 85% 窗口限制）。
*   **工作物理路径**：在向 LLM 投递请求的最后一步同步运行。一旦预估 Token 超过 85%，底座会强行挂起（`await`）当前的推理流程，必须在本地同步生成完摘要并裁剪完历史后，才允许发送网络包。这是防御网关 400 报错的**同步最后防线**。

### 2. 后置后台异步整理 `compressPostChat()`
*   **触发水位**：默认仅为 `postCompressThreshold: 0.65`（已使用 65% 窗口限制）。
*   **工作物理路径**：在大模型回复成功写入 Session 之后运行。由于 65% 水位处于安全区间，底座**绝不阻塞**当前请求，而是启动一个非阻塞的异步 `Promise.then` 挂载到后台锁中静默执行压缩整理。当用户看到字出来时，底座在后台已经默默把老历史整理完毕，保证了交互的心流体验。

## 二、 物理防线：安全截断点回溯算法 (Safe Truncate Index)

在对会话历史（Messages 数组）进行裁剪（Slice）时，很多人会直接调用 `history.slice(safeIndex)`。

### 1. 致命的 Tool Call “意图-结果”因果链断开
在 5.1 节中我们确立了，`assistant` 发起的 `tool_calls` 与紧随其后的 `tool` Observation 结果在协议上具有不可分割的对偶性。
如果我们的截断点恰好落在它们中间：

```
[被裁剪抛弃的区域] ───────> | [assistant: tool_calls (ID: call_101)]
======================== 截断切刀 ========================
[保留发送给 LLM 的区域] ───> | [tool: Observation (ID: call_101)]
```

大模型收到历史后，会发现有一条“凭空出现的 tool 结果”而缺乏上文的 `tool_calls` 意图，大厂网关会立刻抛出协议 400 错误。

### 2. Freya 的解决方案：`findSafeTruncateIndex`
为了防御这一灾难，`compactor.ts` 中设计了极其巧妙的**向前回溯对齐算法**：

```typescript
function findSafeTruncateIndex(history: LLMMessage[], keepTurns: number): number {
  const keepCount = keepTurns * 2;
  if (history.length <= keepCount) return 0;

  // 1. 根据保留轮数粗算一个裁剪索引
  let targetIndex = history.length - keepCount;

  // 2. 💡 物理回溯防线：从粗算点开始向前(老历史方向)扫描
  while (targetIndex > 0) {
    const currentMsg = history[targetIndex];
    const prevMsg = history[targetIndex - 1];

    const isCurrentTool = currentMsg.role === 'tool';
    const isPrevAssistantWithTools =
      prevMsg && prevMsg.role === 'assistant' && !!(prevMsg.toolCalls && prevMsg.toolCalls.length > 0);

    // 如果当前截断边界落在 tool 消息，或前一条是带意图的助手消息
    // 说明此时正处于一个 Tool Call 因果消息对的“肚子”里
    if (isCurrentTool || isPrevAssistantWithTools) {
      targetIndex--; // 强制将切刀向历史更古老的方向推进，直到跨越该因果对
    } else {
      break; // 越过因果对，切刀落在了干净的 User 边界上，安全退出
    }
  }

  // 3. 边界补充校验：防止截断在 user 和并发 toolCalls 中间
  if (targetIndex > 0) {
    const boundaryMsg = history[targetIndex];
    const prevMsg = history[targetIndex - 1];
    if (boundaryMsg.role === 'assistant' && boundaryMsg.toolCalls && boundaryMsg.toolCalls.length > 0) {
      if (prevMsg && prevMsg.role === 'user') {
        targetIndex--;
      }
    }
  }

  return targetIndex; // 返回绝对安全的物理裁剪点
}
```

通过这一层回溯机制，切刀被强制纠正，确保裁剪出来的每一段历史都是逻辑自洽的，在物理上杜绝了多轮工具消息断层引发的崩溃。

## 三、 零额外 CPU 负载：轻量级正则 Token 预估器

为了判定是否触及 85% 压缩线，底座必须频繁估算当前历史的 Token 数。如果每次都调用 Tiktoken C++ 分词包，会导致高并发下服务器的 CPU 负载急剧飙升。

`compactor.ts` 采用了一套极为高超的**正则字符特征预估器**：

```typescript
export function estimateMessageTokens(msg: LLMMessage): number {
  let tokens = 0;
  if (msg.content) {
    // 1. 英文与数字 Token：匹配连续单词数，权重系数设为 1.3
    const englishWords = msg.content.match(/[a-zA-Z0-9_]+/g) || [];
    tokens += englishWords.length * 1.3;

    // 2. 中文字符 Token：匹配汉字个数，根据 UTF-8 编码密度，权重系数设为 1.8
    const chineseChars = msg.content.match(/[\u4e00-\u9fa5]/g) || [];
    tokens += chineseChars.length * 1.8;

    // 3. 特殊控制符、标点与空格：权重系数设为 0.5
    const otherText = msg.content.replace(/[a-zA-Z0-9_]/g, '').replace(/[\u4e00-\u9fa5]/g, '');
    tokens += otherText.length * 0.5;
  }

  // 4. 多模态附件：单张低分辨率图片默认折算为 200 Token
  if (msg.attachments) {
    const imageAttachments = msg.attachments.filter(
      (a) => a.mimeType.startsWith('image/') || a.type === 'image',
    );
    tokens += imageAttachments.length * 200;
  }

  // 5. 工具调用定义与参数字段评估
  if (msg.toolCalls) {
    for (const tc of msg.toolCalls) {
      tokens += 20; // 基准 Token 开销
      if (tc.arguments) {
        const englishWords = tc.arguments.match(/[a-zA-Z0-9_]+/g) || [];
        tokens += englishWords.length * 1.3;
      }
    }
  }

  return Math.ceil(tokens); // 向上取整
}
```

### 物理评估效果：
这套正则估算器拥有接近 $0$ 的 CPU 开销。在实际的压测对比中，其估算出来的 Token 数与 Tiktoken 原生分词结果的偏差**小于 5%**，完全能作为安全水位判定的可靠物理雷达，实现了极致的性能优化。
