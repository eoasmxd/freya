# 7.2 上下文压缩机制：滑动窗口与递归摘要算法

在 7.1 节中，我们了解了长对话超出 Context Window 时对智能体大脑造成的毁灭性灾难。为了物理防御这一问题，底座必须充当“记忆治理器”。

在当前的 Agent 工程实践中，拯救上下文窗口主要有两种技术流派：**滑动窗口淘汰法（Sliding Window）** 与 **主动递归摘要法（Recursive Summarization）**。

它们一个代表了“物理性的遗忘”，另一个代表了“大脑的主动归档”。本节我们将对比解剖这两大算法的设计原理、权衡，并针对摘要机制中的核心缺陷提供防御性的解决方案。

---

## 一、 滑动窗口淘汰法 (Sliding Window)：截断与忘却

滑动窗口淘汰法是一种非常直接的“空间释放”策略。它就像一个 FIFO（先进先出）的固定长度队列。

```
[System Prompt] ── [被踢出的旧消息] <── [ 保 留 的 活 跃 窗 口 (最近 N 轮) ] <── [新进消息]
```

### 1. 技术实现原理
底座设置一个最大消息行数限制 $N$（如 20 行），或者计算 Token 大小。当超过限制时，底座会在回传历史前，**无情地从消息数组的头部（System 消息之后）剔除多余的旧消息**。

### 2. 优缺点评估
*   **优点（运行零开销）**：
    实现极其简单，不需要额外调用大模型去生成整理文本，不产生任何额外的 API 账单费用，执行速度在毫秒级。
*   **缺点（物理性硬遗忘）**：
    这是一种粗暴的遗忘。一旦对话进入第 30 轮，用户在第 2 轮交代的核心账户 ID、偏好设置或刚才修改完的临时代码，会被滑动窗口直接推出边界，彻底被系统遗忘。这对于执行长线复杂业务的智能体来说是无法接受的。

## 二、 主动递归摘要法 (Recursive Summarization)：主动归档

递归摘要法模拟了人类大脑在睡眠时对白天的记忆进行“碎片整理和提炼归档”的过程。

```
[第 1~20 轮对话] ──> 【调用后台大模型摘要】 ──> 生成 summaryText
                                                        │
                                                        ▼
[新的 Context]   ──> [System Prompt] + [summaryText (历史回顾)] + [第 21 轮之后消息]
```

### 1. 技术实现原理
当检测到 Token 逼近安全水位线时，底座执行以下操作：
1.  **截取与保留**：保留最近的 $K$ 条活跃对话消息（如最近 5 条），截取此前的所有老历史消息。
2.  **摘要合成**：将这批老历史送入大模型，配以专用的归档提示词，合成一段紧凑的摘要：`“小明在寻找 101 号订单的退款方法，智能体已调用查询工具，确认退款已到账，小明接下来想修改收货地址。”`
3.  **消息清空与反向插入**：在物理 history 数组中删除这批老历史，织造一条特制的 User 消息：`[此前对话摘要：... ]` 插入到 System 消息之后。
4.  **螺旋递归**：当下一次窗口再次满载，底座将“上一次的旧摘要 + 新的前半段对话”再次打包融合成“新摘要”，螺旋上升，保持上下文总量永远在极小规模。

### 2. 优缺点评估
*   **优点（认知连续性）**：
    旧的历史细节虽然丢了，但**核心的事实、已做出的决策和当前的业务目标被浓缩保存了**。大模型能始终承接长线上下文逻辑，智商表现极其稳定。
*   **缺点（二次账单与细节磨灭）**：
    为了合成摘要，底座必须频繁地在后台异步调用大模型，这会产生额外的 API Token 费用。更致命的是，摘要由大模型生成，如果摘要 Prompt 写得不好，大模型极易在提炼时丢失重要的具体数据（如 IP 地址、文件路径或金额数字），发生“细节磨灭”。

## 三、 【架构防御】防御“事实磨灭与时序失真”的摘要模板设计

在实际智能体运行中，递归摘要法如果提示词不当，极易引发以下两类核心缺陷：
*   **事实丢失**：对话中的具体结论或行动被大模型泛化模糊处理（如将“用户修改了配置文件 config.json 中的 port 为 8080”粗略概括为“用户进行了配置调整”）。
*   **时序矛盾**：增量融合时新旧决策倒错，导致大模型在后续决策中产生自相矛盾的逻辑幻觉。

### 🌟 物理模板规范：`core.prompt.summarize_guidance.md`
根据 Freya 的“零硬编码提示词（Zero Hardcoded Prompt）”规范，摘要提炼指令独立存放于物理文件 `packages/core/config/prompts/core.prompt.summarize_guidance.md` 中，通过提示词注册表动态加载：

```markdown
请将上述对话中的核心交互关键信息提炼为一段极简的背景摘要（50字以内），作为下一步推理的参考背景。
如果当前已经存在先前的背景提要，请将新内容增量融合成一段连贯的新提要。

【摘要提炼要求】
1. 事实聚焦：聚焦于已发生的具体行动、得出的核心结论、当前的状态以及待办的事实，去除所有的口水话、客套辞令及推理过程。
2. 保持连贯：增量融合时，要确保时序正确、逻辑紧凑，避免重复陈述或产生自相矛盾的信息。
```

### 物理设计优势：
1. **去口水话与极致紧凑**：通过“50字以内”与“去除推理过程”约束，将历史背景的 Token 开销压缩到极低基线，为后续新工具调用预留足够的窗口余量。
2. **时序与结论锚定**：明确要求“增量融合时确保时序正确”，避免反复压缩导致前后因果断裂，最大化保障智能体在超长多轮对话中的认知稳定性。
