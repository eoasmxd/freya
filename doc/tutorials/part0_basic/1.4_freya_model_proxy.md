# 1.4 【沙箱对照】阅读与调试模型代理配置

在前面的章节中，我们分别解剖了大模型 API 的无状态拼接原理和 Chat Completion 规范中 Message 的物理格式。但是在实际开发智能体底座时，我们不能把这些繁琐的接口调用和厂商参数直接暴露给上层的 Agent Executor 决策环。

因为在生产环境中，你随时需要：
*   在不同的模型提供商（如 OpenAI、Gemini、DeepSeek）之间自由切换。
*   屏蔽不同模型的参数字段差异（有些模型支持 `top_k`，有些则不支持）。
*   **服务高可用降级**：当默认的模型发生限流（Rate Limit）或服务商宕机时，系统必须自动熔断并降级到备用模型。
*   **多模态降级回退**：当把包含图片的附件消息发给不支持多模态的廉价模型时，系统能自动将附件转化为文本描述，防止 API 报错拒绝。

本节我们将对照阅读 Freya 的核心模型代理层源码 `packages/core/src/llm/llm-proxy.ts`，看看底座是如何通过优雅的架构设计解决上述所有工程难题的。

---

## 一、 架构心脏：FreyaLLMProxy 类的物理职责

在 Freya 沙箱中，`FreyaLLMProxy` 实现了 SDK 中定义的统一大模型服务契约接口 `ILLMService`。

它是整个智能体的心脏。所有上层组件（如会话压缩、心智推理死循环）在需要调用大模型时，都不直接访问 OpenAI 或 Gemini 的插件，而是统一调用 `FreyaLLMProxy.chat()` 方法。

让我们看它的核心属性结构：
```typescript
export class FreyaLLMProxy implements ILLMService {
  private llmLogger: FreyaLLMLogger;
  // 核心健康状况注册表：映射 "provider:model" -> 它的物理健康状态
  private modelHealthRegistry = new Map<string, HealthState>();

  constructor(
    private llmRegistry: FreyaLLMRegistry,
    private context: FreyaContext
  ) {
    this.llmLogger = new FreyaLLMLogger(!!this.context.config.log?.llm);
  }
}
```

## 二、 带降级熔断链的 chat() 执行控制流

当 `chat()` 方法被调用时，它会在内存中动态组装一条**候选降级链**。一旦主模型报错，底座会立刻切换到备用模型继续请求，整个过程对上层 Agent 完全透明。

### 1. 物理源码逻辑拆解
让我们阅读 `chat()` 方法的核心实现：

```typescript
async chat(
  messages: LLMMessage[],
  tools?: ToolDefinition[],
  options?: LLMOptions
): Promise<{ message: LLMMessage; usage?: LLMTokenUsage }> {
  // 1. 动态构建出排序好的候选模型链
  const modelChain = this.buildModelChain(options);
  let lastError: any = null;

  for (const candidate of modelChain) {
    const currentProviderId = candidate.provider;
    const currentModelId = candidate.model;

    try {
      // 2. 根据当前模型的多模态能力处理消息附件 (降级回退)
      const processedMessages = this.prepareMessagesForModel(messages, currentModelId, currentProviderId);

      // 3. 执行真正的底层调用
      const result = await this.executeChat(processedMessages, tools, {
        ...options,
        providerId: currentProviderId || undefined,
        modelId: currentModelId || undefined
      });

      // 4. 调用成功，恢复该模型的健康标记
      this.modelHealthRegistry.set(`${currentProviderId}:${currentModelId}`, {
        type: 'healthy',
        lastSuccessTime: Date.now()
      });

      return result;
    } catch (err: any) {
      lastError = err;
      // 5. 发生错误，分类判断是 fatal (如API key错误) 还是 temporary (如限流/网络异常)
      const errorType = this.classifyError(err);
      if (errorType === 'fatal') {
        this.modelHealthRegistry.set(`${currentProviderId}:${currentModelId}`, {
          type: 'fatal_failed',
          errorMessage: err.message || String(err)
        });
      } else {
        this.modelHealthRegistry.set(`${currentProviderId}:${currentModelId}`, {
          type: 'temporary_failed',
          lastFailedTime: Date.now(),
          errorMessage: err.message || String(err)
        });
      }
      this.context.logger.warn(
        `[FreyaLLMProxy] 模型 [${candidate.name}] 调用遭遇 [${errorType}] 级异常，已熔断避让: ${err.message}`
      );
    }
  }

  throw lastError || new Error('所有候选模型均调用失败，无可用备选。');
}
```

### 2. 核心降级评分算法分析
`buildModelChain()` 内部实现了一套巧妙的健康度排序机制：
*   **正常模型（未报错过）**：评分设为 `1`。
*   **发生致命错误（fatal，如 API Key 过期）**：评分直接设为 `-99999999`，确保该模型在进程的当前生命周期内**彻底被拉黑，绝不再次调用**，直到人工更换配置。
*   **发生临时错误（temporary，如 502 网络抖动）**：如果发生在 `5 分钟` 冷却期（Cooldown）内，评分设为 `-100`（靠后排队）；如果超出 5 分钟，评分恢复为 `0` 允许再次尝试。
*   **成功模型**：评分设为它的上次成功时间戳，使经常成功运行的模型排在降级链最前方。

## 三、 参数清洗与异构模型参数抹平

不同厂商的参数在配置文件中杂乱无章。例如在 `models` 配置中：
*   有些模型写了计费价格 `inputPrice`、位置编码上限 `contextWindow`、多模态能力 `capabilities`。
*   有些模型写了自定义的采样控制参数。

Freya 在 `executeChat()` 中执行了极富智慧的**解构与清洗**：

```typescript
const {
  id: _id,
  name: _name,
  inputPrice: _ip,
  outputPrice: _op,
  cachedInputPrice: _cip,
  contextWindow: _cw,
  contextTokens: _ct,
  capabilities: _cap,
  ...cleanModelConfig // 💡 动态解构：剥离元数据，只保留干净的大模型调用参数
} = modelConfig as any;

const enrichedOptions: LLMPluginOptions = {
  ...options,
  modelId,
  providerConfig: {
    apiKey: providerConfig.apiKey,
    baseURL: providerConfig.baseURL
  },
  modelParams: {
    ...cleanModelConfig, // 全局配置里的默认参数 (如 temperature)
    ...options?.modelParams // 用户单次调用临时覆盖的参数
  }
};
```
通过这种参数清洗，被传给底层大模型驱动插件的 `modelParams` 只包含诸如 `temperature`、`top_p` 等纯净的参数，去除了计费和特征标记等元数据干扰，从而以极高内聚的方式抹平了厂商差异。

## 四、 物理附件降级机制 (Capabilities Downgrade)

在多模态 Agent 时代，用户经常发送图片或音频附件。如果大模型并不支持这些模态，强行发送 Base64 数据包会导致网络 API 报错拒绝。

在 `prepareMessagesForModel()` 中，Freya 展示了底座如何巧妙地兼容低配模型：

```typescript
private prepareMessagesForModel(
  messages: LLMMessage[],
  modelId: string,
  providerId: string
): LLMMessage[] {
  // 1. 获取目标大模型的能力声明 (如是否支持 ['image', 'audio'])
  const capabilities = this.getModelCapabilities(modelId, providerId);
  const hasImageCapability = capabilities.includes('image');

  return messages.map((msg) => {
    if (msg.role !== 'user' || !msg.attachments || msg.attachments.length === 0) {
      return msg;
    }

    let newContent = msg.content || '';
    const keptAttachments: any[] = [];

    for (const attach of msg.attachments) {
      const isImage = attach.mimeType.startsWith('image/') || attach.type === 'image';
      // 2. 如果发送的是图片，但当前候选模型不支持多模态
      if (isImage && !hasImageCapability) {
        if (attach.description) {
          // 3. 将图片的文字描述，反向追加到 user 消息的纯文本中 (降级退回文本模式)
          newContent = `${newContent}\n${attach.description}`.trim();
        }
      } else {
        keptAttachments.push(attach);
      }
    }

    return {
      ...msg,
      content: newContent,
      attachments: keptAttachments.length > 0 ? keptAttachments : undefined
    };
  });
}
```

本节通过阅读 Freya 的核心源码，我们得以亲眼见证一个健壮的智能体底座是如何在物理层面将零乱、多变且不可靠的大模型网络服务封装为统一、可用且带自动容灾能力的确定性接口的。这一模型代理层，将成为我们下一章探索 Agent 心智大脑（ReAct 执行器）最为坚实的底盘。
