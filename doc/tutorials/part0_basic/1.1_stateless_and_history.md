# 1.1 鱼的记忆与无状态网络

当我们与市面上的智能体进行多轮对话，感觉它能完美记住我们前几轮说过的话，甚至能承接上文的语境来进行深度探讨时，我们会习惯性地认为：“大模型在大脑里为我开辟了一块记忆区，正记着我俩的聊天历史”。

然而，这又是一个美丽的工程伪装。

真实世界里的大模型，拥有像鱼一样的记忆 —— 它的记忆时间只有 **0 秒**。

---

## 一、 网络层面的无状态（Stateless）本质

在底层，所有大模型厂商提供的聊天接口（例如 OpenAI 的 `/v1/chat/completions` 接口或 Gemini 的 `generateContent` 方法）都是标准的 **RESTful API**。它们运行在无状态的 HTTP 协议之上。

### 1. 什么是无状态服务？
**无状态（Stateless）** 意味着：**服务器在处理当前请求时，完全不依赖、也不保存任何历史请求所产生的上下文状态。**

对于大模型服务器而言，每一次你发起的 API 请求，在物理上都是一次完全独立的计算任务：
1.  显卡从 HBM（高带宽显存）中读取模型数十亿的权重参数。
2.  将你本次请求发送的所有文本编码成 Token 向量，塞入 GPU 显存。
3.  通过自注意力机制进行 Next-Token 预测。
4.  将计算出的概率结果（文字）通过网络流式吐回给你的客户端。
5.  **在逻辑层关闭属于你本次请求的会话生命周期，彻底忘记你曾经来过。**（注：虽然云端推理引擎可能会在显存中将你请求的静态提示词前缀短暂缓存以待下次复用，但从 API 接口的逻辑来看，你的下一次请求依然是一个全新、孤立的事件。）

```
请求 1: 客户端 ───发送: "我是小明" ───> 【无记忆大模型】 ───返回: "你好，小明！" ───> 显存瞬间清空
请求 2: 客户端 ───发送: "我是谁？" ───> 【无记忆大模型】 ───返回: "我不知道你是谁。" ───> 显存瞬间清空
```

无论你在请求中表现得多么亲密，对于大模型来说，下一次请求永远是它与你的“初次相见”。

---

## 二、 多轮会话记忆是如何凭空制造的？

既然大模型本身秒删一切历史，为什么我们还能和智能体进行多轮对话呢？

答案是：**智能体系统的工程底座在暗中替我们“负重前行”**。底座必须在本地（或数据库）把过去的每一轮聊天记录完整保存下来。当用户发起第 $N$ 次提问时，底座在发送请求前，会**强行把之前的所有聊天历史以 Message 列表的形式，重新打包拼接在本次问题的前面，作为一个庞大的文本块一次性发给大模型。**

### 1. 历史拼接的物理演变过程
让我们以三次连续的对话为例，看看发给 API 的 Raw 数据包是如何随着多轮对话变得越来越臃肿的：

#### 第一轮对话：
*   **用户输入**："我叫小明，是一个程序员。"
*   **底座发给大模型 API 的数据**：
    ```json
    [
      {"role": "user", "content": "我叫小明，是一个程序员。"}
    ]
    ```
*   **大模型返回**："你好，小明！程序员是个充满挑战的职业。"

#### 第二轮对话：
*   **用户输入**："我平时最喜欢用什么语言写代码？"
*   **底座发给大模型 API 的数据**（底座将第一轮的历史打包回传）：
    ```json
    [
      {"role": "user", "content": "我叫小明，是一个程序员。"},
      {"role": "assistant", "content": "你好，小明！程序员是个充满挑战的职业。"},
      {"role": "user", "content": "我平时最喜欢用什么语言写代码？"}
    ]
    ```
*   **大模型返回**："你刚才没告诉我你最喜欢的语言，请问是 TypeScript 吗？"

#### 第三轮对话：
*   **用户输入**："是的，我最喜欢 TypeScript。"
*   **底座发给大模型 API 的数据**（底座将前两轮的所有历史打包回传）：
    ```json
    [
      {"role": "user", "content": "我叫小明，是一个程序员。"},
      {"role": "assistant", "content": "你好，小明！程序员是个充满挑战的职业。"},
      {"role": "user", "content": "我平时最喜欢用什么语言写代码？"},
      {"role": "assistant", "content": "你刚才没告诉我你最喜欢的语言，请问是 TypeScript 吗？"},
      {"role": "user", "content": "是的，我最喜欢 TypeScript。"}
    ]
    ```

大语言模型正是通过重新阅读我们帮它回传的**历史聊天剧本**，才能够在“接龙”时承接小明、程序员、TypeScript 等关键字，假装自己拥有了“记忆”。

## 三、 二次方级（Quadratic）Token 计费与带宽膨胀

这种“历史全量回回传”的物理机制，在带来连贯会话体验的同时，也带来了一个可怕的工程代价：**输入 Token 数量的非线性飙升**。

### 1. 什么是二次方级开销？
在一次正常的 10 轮对话中，假设每一轮用户输入和模型回答各消耗 100 Token。
*   第 1 轮：大模型需要处理 **100** Token 的输入。
*   第 2 轮：大模型需要处理 **300** Token（前一轮的 200 + 新输入的 100）。
*   第 3 轮：大模型需要处理 **500** Token。
*   ...
*   第 10 轮：大模型需要处理 **1,900** Token。

在 10 轮交互中，我们仅在**输入端**就累计产生了 **10,000 Token** 的计费：

$$100 \text{ (第1轮)} + 300 \text{ (第2轮)} + 500 \text{ (第3轮)} + \dots + 1,900 \text{ (第10轮)} = 10,000 \text{ Token (输入)}$$

如果加上每轮模型吐出的 100 Token 输出（累计 $10 \times 100 = 1,000$ Token），整场会话最终产生的计费总额达到了 **11,000 Token**！

```
Token 计费开销增长示意:

第 1 轮: [■] (100)
第 2 轮: [■■■] (300)
第 3 轮: [■■■■■] (500)
第 4 轮: [■■■■■■■] (700)  <── 输入总量呈阶梯式非线性膨胀！
```

用户实际只说了 10 句话，由于“全量历史回传”的物理机制，API 计费账单却膨胀了 5.5 倍。随着对话轮数的增加，**网络带宽的吞吐压力与计费开销呈二次方级暴涨，每次请求的延迟（TTFT）也会越来越大**。

## 四、 【调试与避坑】历史拼接中的网关校验与协议陷阱

在手动拼接多轮对话历史时，初学者如果直接用数组 push 消息，极易触发大模型 API 的网关格式校验限制，导致程序返回 `400 Bad Request` 报错。

以下是两个我们在实际开发中必须拦截的典型协议大坑：

### 1. 连续相同角色的格式报错
许多大模型厂商（如 Anthropic Claude、Gemini）的 API 对 Message 数组的角色交替性有极其严格的格式校验。它们要求**数组中必须是 `user` 与 `assistant` 轮流出现，绝对不允许连续两个相同角色（如连续两个 `user`）相连**。

```json
// ❌ 错误示范：会导致 API 报错 400
[
  {"role": "user", "content": "我的猫叫咪咪。"},
  {"role": "user", "content": "它今年三岁了。"}  // 连续两个 user，报错！
]
```

*   *工程防御策略*：在底座拼接历史时，必须引入一个**消息合并净化器（Message Cleaner）**。如果检测到用户因为网络重试或连续发送，导致出现了两个连续的 `user` 消息，必须在发送前将它们的 `content` 合并为单个 Message，或者在中间插入一个空白的 `assistant` 回应占位符。

### 2. 首尾角色错位陷阱
大模型的聊天 API 强硬规定：**Message 数组的第一个消息（除了 System 外）必须是 `user` 角色发起的，且最后一个消息也必须是 `user` 角色发起的（除非是为了引导模型输出而故意遗留 assistant 作为后缀）**。
*   如果将一个以 `assistant` 开头的消息列表发给 API，有些严格的网关会直接拒绝请求。
*   *工程防御策略*：底座在发送前需校验并裁剪数组，确保首尾消息符合大厂网关的安全要求。

建立起“网络无状态、记忆靠拼接”的物理认知后，我们就拿到了开启智能体大脑的钥匙。在接下来的小节中，我们将进一步拆解在这个聊天舞台上活跃的 system、user 和 assistant 三大角色的数据流奥秘。
