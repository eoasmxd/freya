# 0.1 概率预测与 Next-Token Prediction

当我们与各种号称具备“通用人工智能（AGI）”的智能体（Agent）对话时，它们那行云流水、仿佛充满智慧的回答常常让我们产生一种错觉：大语言模型（LLM）正像人类一样在思考。

然而，拉开这层温润的拟人化面纱，智能体的大脑深处其实只在物理性地重复着一个单调而朴素的动作 —— **文字接龙**。

---

## 一、 概率预测与自回归（Autoregressive）机制

大语言模型（LLM）的本质，是一个基于海量文本训练出来的**概率预测概率分布模型**。它的终极任务非常简单：**给定一段已知的上文，预测下一个可能出现的词（或字符）的概率分布**。

### 1. 自回归的物理数学公式
在数学上，这一过程被称为**自回归（Autoregressive）**模型。其概率计算公式可以表示为：

$$P(w_t \mid w_1, w_2, \dots, w_{t-1})$$

其中：
*   $w_1, w_2, \dots, w_{t-1}$ 代表输入给大模型的历史所有文本（即上下文，Context）。
*   $w_t$ 代表即将生成的第 $t$ 个词。
*   $P$ 则是在给定上述已知历史的条件下，生成 $w_t$ 的概率。

当模型通过这一公式预测出第 $t$ 个词后，会立即将这个新词拼接到原本的输入上，重新作为新的“已知上下文”，再次喂给大模型，去预测第 $t+1$ 个词。这种“左手倒右手、自我回归、循环迭代”的生成机制，就是大模型产生连续文本的底层逻辑。

```
已知输入: "今天天气真" ───> 【LLM 大脑】 ───> 预测下一个字概率: {"好": 85%, "晴": 10%, "糟糕": 5%}
                                                    │
                                                    ▼ (选中 "好")
新输入: "今天天气真好" ───> 【LLM 大脑】 ───> 预测下一个字概率: {"，": 90%, "。": 8%, "了": 2%}
```

### 2. 为什么自回归机制决定了 Agent 的基本形态？
这种“Next-Token Prediction（下一个词预测）”的物理局限性，直接决定了 Agent 的两个最底层特性：
1.  **无状态性（Stateless）**：大模型就像一个函数计算，对于相同的输入和参数，它吐出的概率分布是确定的。它本身是不具备“时间”概念的，每次请求它都记不得上一次你是谁。因此，多轮会话（Session）的记忆完全依赖于我们在客户端源源不断地把历史聊天记录拼接成一个巨大的上下文重新发送。
2.  **累积误差（Error Accumulation）**：因为第 $t$ 个词的生成依赖第 $t-1$ 个词。一旦大模型在中间某一步预测出了一个逻辑错误的词，这个“错误”就会被当作既定事实重新塞回输入，引发后面的多米诺骨牌效应。这也就是为什么智能体在规划任务时容易陷入“鬼打墙”或中途跑偏的原因。

## 二、 什么是 Token 与 Tokenizer 的工作原理

大模型是不能直接看懂“今天天气真好”或者 "Hello World" 这些自然语言字符的。在大模型内部，所有的文字都需要被转化成高维的数学向量（Embeddings）。而在这两者之间起到翻译官作用的，就是 **Tokenizer（分词器）**。

### 1. Token 的定义
**Token** 是大语言模型处理文本的最小语义单元。一个 Token 可以是一个完整的单词（如 `apple`）、一个词根（如 `un`）、一个单字（如 `好`），甚至可以是一个标点符号，或者一串空格。

大模型在训练前会确定一个**词表（Vocabulary）**，词表里收集了几万到几十万个常用的 Token 单元，每个 Token 都有一个唯一的整数 ID 对应。例如：
*   `"the"` 对应 ID `1824`
*   `"apple"` 对应 ID `7362`
*   `"好"` 对应 ID `32890`

### 2. Byte-Pair Encoding (BPE) 算法机制
现代大模型（如 GPT-4, Llama 3）大多使用 **BPE（字节对编码）** 算法来切分 Token。BPE 的核心逻辑是从字节级别开始，通过统计学方法逐步合并高频出现的字符对：

1.  **初始化**：将词表初始化为所有基本的字符（如 256 个 ASCII 码或 UTF-8 基础字节）。
2.  **统计与合并**：扫描训练语料，统计相邻字符对（如 `e` 和 `s`）的出现频次，将最高频的组合合并成一个新的 Token（如 `es`）。
3.  **循环往复**：重复合并步骤，直到词表大小达到设定阈值（例如 100,000 个 Token）。

通过这种方式，高频单词如 `"the"`、`"and"` 会被合并为一个 Token，而低频词或生僻词（如 `"antigravity"`）则会被拆分为多个 Token（如 `anti` + `gravity`）。这保证了词表既不会无限膨胀，又不会因为遇到生僻词而无法解析。

## 三、 中英文 Token 的底层物理差异

作为 Agent 开发者，我们需要深刻意识到中英文在 Tokenize 上的物理差异。这种差异**本质上取决于分词器（Tokenizer）的词表大小与训练语料比例的设计，而非语言或模型能力本身的缺陷**。由于大模型 API 的**上下文限制（Context Window）**和**计费**都是基于 Token 数量而非字符数计算的，因此分词器的设计对 Agent 的研发成本和窗口管理起着决定性作用。

### 不同分词器下的中英文密度差异

*   **旧世代分词器的设计局限（以 OpenAI `cl100k_base` 为例）**：
    由于早期的分词器训练语料中英文占比超过 95%，且词表容量较小（如 100k），导致英文的切分效率极高（通常 **1 个 Token 约等于 4 个英文字符**，或者 0.75 个英文单词）。而中文由于紧凑且没有物理空格，大部分汉字无法在词表中合并为词组，甚至部分汉字会因找不到而退化为原始 UTF-8 字节进行解析（在 UTF-8 中 1 个汉字占 3 字节，直接变成 3 个 Token 的惨烈消耗）。
    在此类分词器下，在表达相同的语义信息量时，中文往往比英文需要多消耗约一倍的 Token 数量，这也影响了会话窗口的留存深度。

*   **大词表与多语言优化分词器（以 `o200k_base` 及国产模型分词器为例）**：
    随着词表容量扩充（如 GPT-4o 采用的 200k 词表）以及中文训练语料占比的大幅提升，新一代分词器和国产大模型（如 DeepSeek、Qwen 等）对中文分词效率进行了针对性的深度优化。
    在这些新型分词器中，大量的中文常用单字和词组被直接收录为单个 Token（1 个汉字平均仅消耗 0.3 到 0.6 个 Token）。在表达相同语义时，中文与英文的 Token 消耗量已基本处于对等状态，甚至在特定的精炼中文表述中，中文的 Token 承载率会比英文更高。

在进行 Agent 架构设计和预算预估时，应当针对所选模型的分词器特性进行实际测试，以获得准确的 Token 消耗模型。

## 四、 【代码实验】中英文 Token 密度的物理测量

为了严谨，我们直接用代码在本地测试不同文本的 Token 切分情况，拒绝自我想象。

在 Node.js 环境下，我们可以使用纯 JavaScript 编写的官方分词器 **`js-tiktoken`** 。

在运行本段实验前，您需要先在脚本所在的目录下执行以下命令安装该依赖包：

```bash
npm install js-tiktoken
```

### 1. 实验代码 (token_test.js)
```javascript
const { getEncoding } = require("js-tiktoken");

// 初始化 GPT-4 (cl100k_base) 和 GPT-4o (o200k_base) 分词器
const cl100k = getEncoding("cl100k_base");
const o200k = getEncoding("o200k_base");

const englishText = "Hello, World! Welcome to the world of AI Agents.";
const chineseText = "你好，世界！欢迎来到智能体的物理世界。";

console.log("==================== 1. 英文文本测试 ====================");
console.log(`文本内容: "${englishText}"`);
console.log(`字符长度 (Length): ${englishText.length}\n`);

const eng100k = cl100k.encode(englishText);
const eng200k = o200k.encode(englishText);

console.log(`[旧版 cl100k_base (GPT-4)] -> Token 数: ${eng100k.length} | 密度比: ${(englishText.length / eng100k.length).toFixed(2)}`);
console.log(`[新版 o200k_base (GPT-4o)] -> Token 数: ${eng200k.length} | 密度比: ${(englishText.length / eng200k.length).toFixed(2)}\n`);

console.log("==================== 2. 中文文本测试 ====================");
console.log(`文本内容: "${chineseText}"`);
console.log(`字符长度 (Length): ${chineseText.length}\n`);

const ch100k = cl100k.encode(chineseText);
const ch200k = o200k.encode(chineseText);

console.log(`[旧版 cl100k_base (GPT-4)] -> Token 数: ${ch100k.length} | 密度比: ${(chineseText.length / ch100k.length).toFixed(2)}`);
console.log(`[新版 o200k_base (GPT-4o)] -> Token 数: ${ch200k.length} | 密度比: ${(chineseText.length / ch200k.length).toFixed(2)}`);
```

在终端执行以下命令运行该脚本：

```bash
node token_test.js
```

### 2. 测量结果与痛点分析
运行上述代码，你将直观地看到：
*   **英文文本表现稳定**：在两代分词器下，英文字符数均为 48 个，切分出的 Token 数量均为 **12 个**（字符/Token 密度比均为 **4.00**），说明词表容量升级对结构成熟的英文文本压缩影响不大。
*   **中文文本优化显著**：中文字符数为 19 个。在旧版 `cl100k_base` 下，由于高频词未合并，切分出多达 **24 个 Token**（密度比仅为 **0.79**）；而在新版 `o200k_base` 下，因为常用汉字与词组并入词表，Token 数量暴降至 **13 个**，密度比直接拉升到 **1.46**，降幅达到近 45%。

> [!NOTE]
> 需要注意的是，本实验仅展示了以 OpenAI 模型体系为代表的两代分词器。在实际的 Agent 研发中，不同的模型厂商会使用完全不同的分词器。特别是专门针对中文语料进行深度优化的国产大模型（如 DeepSeek、Qwen 等），其分词器对中文汉字的压缩率通常会更高（一个汉字有时仅消耗 0.3 到 0.5 个 Token）。因此在对接其他厂商的模型时，应当根据其对应分词器的真实表现进行评估。
>
> 此外，虽然本教程（Freya 项目）为了便于教学讲解，其内置系统提示词均采用中文编写，但这并不意味着中文提示词在指令遵循和推理性能上优于英文。现阶段对于大多数国际主流基座模型而言，英文提示词在逻辑推理、格式约束和长文本遵循上依然更具优势。在生产环境部署中，建议开发者根据所使用模型的语言偏好，将提示词优化并翻译为英文以追求更佳的性能。

### 3. “Token 刺客”排查防范
在 Agent 实际工程中，有以下两个最容易被忽略的“Token 刺客”，它们会在暗中吃掉你的上下文配额：
1.  **JSON 缩进与冗余字符**：
    为了方便阅读，我们常常将 API 传递的数据格式化为带有换行和四个空格缩进的 JSON。在大模型眼中，**连续的空格和换行符同样也是 Token**。一个格式化优美的 JSON 数据可能会包含成百上千个无意义的空格 Token。
    *   *防御手段*：在喂给大模型前，必须使用 `JSON.stringify(data)` 进行紧凑压缩，抹去所有换行和缩进。
2.  **Markdown 表格与标点**：
    复杂的表格边框符号（如 `|`、`-`）会产生高频碎片 Token。
    *   *防御手段*：非必要时不传大量原始表格数据，可以转换为更紧凑的 CSV 格式或简明文本列表送入。

通过本节的物理剖析，你应该明白：**大模型是用概率在“接龙”，而它的世界尺度是 Token。** 建立起这个物理认知，是我们后续开发任何高内聚 Agent 架构（如 ReAct、记忆池）的重要逻辑基石。
