# 9.1 链路级刹车机制

在大模型流式交互和 ReAct 循环执行中，我们经常会遭遇以下三种大模型“暴走”的物理场景：
*   **大模型“抽风”**：大模型开始在屏幕上流式输出一万行毫无意义的乱码或者重复文字（鬼打墙）。
*   **工具执行过慢**：智能体在后台调用了一个极为缓慢的数据库查询接口，已经转圈了 10 秒。
*   **用户改变了主意**：智能体打字打到一半，用户突然意识到自己提问打错字了，在前端紧急点击了“停止生成（Stop）”按钮。

如果在底座架构中，我们没有建立起一套**链路级的紧急刹车机制**：
*   即使前端用户关掉了网页，大模型在云端服务器依然会继续推理，**疯狂燃烧你的 Token，直到输出额度爆满，产生高昂账单**。
*   底座正在进行的慢速本地工具依然会顽固地把 CPU 和内存占满，直到运行结束，这会产生大量无用的“僵尸计算”。

为了在物理层面上解决智能体交互链路中的紧急中断控制，底座必须建立起基于 **`AbortController` / `AbortSignal`** 的刹车网络。

---

## 一、 AbortSignal：贯穿大脑与躯体的“物理刹车拉线”

在 Web 标准中，`AbortController` 提供了对异步操作的通用中断接口。在 Freya 底座中，`AbortSignal` 被当成了一根**贯穿整个智能体神经网络、决策执行器和本地工具进程的核心刹车拉线**：

```
                              [ 用户点击 "停止" 按钮 ]
                                         │
                                         ▼ (触发 AbortController.abort())
                     ┌───────────────────┴───────────────────┐
                     ▼                                       ▼
             [网络传输层 (Fetch)]                     [核心执行器层 (ReAct)]
                     │                                       │
           TCP RST 包强制重置网络连接               while(loop) 中断逻辑因果链
                     │                                       │
                     └───────────────────┬───────────────────┘
                                         ▼
                               [本地工具层 (Tool Process)]
                                         │
                                  销毁僵尸子进程与文件流
```

### 1. 第一层：网络传输层 (Network Pipe)
当底座向大模型 API 发起 SSE 流式 fetch 请求时，必须将 `signal` 作为配置参数传入：

```typescript
const controller = new AbortController();

// 💡 物理挂接：将刹车拉线绑定到 fetch 请求中
const response = await fetch(requestUrl, {
  method: 'POST',
  body: JSON.stringify(requestBody),
  signal: controller.signal // 绑定信号
});
```

当控制器执行 `controller.abort()` 时，Node.js 底层网络库会在物理上立刻向大模型 API 服务器发送一个 **TCP RST (复位) 重置数据包**。
这会瞬间强行切断与大模型的物理 TCP 连接，迫使云端 API 服务器瞬间终止推理，从根本上锁死 Token 计费。

### 2. 第二层：核心执行器层 (Executor Loop)
在 2.3 节我们剖析了核心执行器的 `while(loop)` 自循环。在并发工具调度或多步迭代中，执行器必须在每一步的开头以及 `await` 之后，高频检查刹车信号的物理状态：

```typescript
// 💡 物理自检：如果信号已经被拉起，立刻退出 ReAct 死循环
if (this.context.signal.aborted) {
  this.logger.info("[AgentExecutor] 检测到链路刹车信号，紧急退出决策循环。");
  break;
}
```

### 3. 第三层：本地工具层 (Tool Execution)
底座在调度本地工具执行时，会将当前的 `context`（包含 `signal` 句柄）作为执行上下文注入函数。
工具内部（例如执行大文件下载或数据库查询）在进行耗时操作时，也必须对该信号进行监听自检，或者将其向下透传给如 `child_process` 子进程或数据库驱动，确保手动刹车时能立刻释放操作系统 CPU 算力，防止出现僵尸进程。

## 二、 底座层“多路刹车分发”的设计：`FreyaAgentService`

在大并发的多会话智能体环境中，我们绝不能使用全局共享的 `AbortController`，否则会话 A 触发停止，会导致正在运行的会话 B 被无差别误杀。

在 Freya 源码 `packages/core/src/agent/agent-service.ts` 中，底座通过 `abortControllers` Map 维护每个会话的专属控制器，并借助 EventBus 实现完全解耦的**事件驱动中断分发**：

```typescript
// 摘自 packages/core/src/agent/agent-service.ts
export class FreyaAgentService {
  // 维护每个活跃会话的独立中断控制器
  private abortControllers = new Map<string, AbortController>();

  private setupListeners(): void {
    // 监听总线派发的中断事件
    this.context.eventBus.on('session:interrupt', (payload: { sessionId: string }) => {
      // 1. 清空当前会话尚未处理的消息队列
      this.messageQueues.delete(payload.sessionId);

      // 2. 提取当前主会话的控制器并触发强行中断
      const controller = this.abortControllers.get(payload.sessionId);
      if (controller) {
        controller.abort();
        this.context.logger.warn(`[AgentService] 已打断会话 ${payload.sessionId} 的生成流。`);
        this.abortControllers.delete(payload.sessionId);
      }

      // 3. 级联打断属于该会话的所有子智能体分支 (Sub-Agents)
      for (const [key, childCtrl] of this.abortControllers.entries()) {
        if (key.startsWith(`${payload.sessionId}_sub_`)) {
          childCtrl.abort();
          this.abortControllers.delete(key);
          const subSessionId = key.substring(`${payload.sessionId}_sub_`.length);
          this.sessionManager.updateSession(subSessionId, { status: 'failed', durationMs: 0 }).catch(() => { });
          this.context.logger.warn(`[AgentService] 已级联打断子智能体会话 ${subSessionId}`);
        }
      }
    });
  }
}
```

### 物理设计优势：
1. **通道完全解耦**：无论是 Web 前端点击“停止”，还是 Telegram、微信通道发来 `/stop` 命令，通道插件只需向总线触发 `eventBus.emit('session:interrupt', { sessionId })`，无需感知内部具体如何执行中断。
2. **级联树形中断**：不仅能打断当前主执行器，还能顺带将该会话衍生派生的所有子智能体任务全部安全熔断，彻底杜绝后台算力泄露。

## 三、 【避坑指南】防止 Abort 后网络连接僵尸残留 (TCP Leak)

在开发中，很多开发者觉得自己调用了 `controller.abort()`，Node.js 就会打点好一切。

### 1. 僵尸链接（Zombie Connections）隐患
如果你的大模型插件使用的是第三方厂商封装的旧版 SDK，它们虽然在表面上接受了 `signal`，但其内部的 HTTP 请求实现（例如使用了未正确适配 Web API 标准的 `axios` 或老版 `http.request`）**并没有在捕获到 abort 信号时显式调用 socket.destroy()**。
*   **物理惨剧**：尽管前端展示了“已停止生成”，但服务器后台与大模型 API 之间的 TCP 长链接其实**依然在默默下载数据并保持保活（Keep-Alive）状态**。
*   高并发下，这会在操作系统底层产生大量的“僵尸连接（Zombie Connections）”，迅速耗尽操作系统的物理文件描述符限制（FD Limit），导致整个 Web 服务器无法再接受任何新连接，发生雪崩瘫痪。

### 2. 避坑策略：底座层物理强制销毁
底座在封装网络请求时，切不可完全信任第三方 SDK。我们必须设立一道底层的**强制销毁保底防线**：

```typescript
// 💡 底层物理强制销毁防线
const socketTimeoutSignal = AbortSignal.timeout(90000); // 90秒强制超时信号
const clientSignal = options?.signal;

// 1. 利用 Node.js 22+ 的 AbortSignal.any() 缝合用户停止信号与超时信号
const combinedSignal = clientSignal 
  ? AbortSignal.any([clientSignal, socketTimeoutSignal]) 
  : socketTimeoutSignal;

const response = await fetch(requestUrl, {
  method: 'POST',
  body: JSON.stringify(requestBody),
  signal: combinedSignal
});

// 2. 如果发生了 abort，强制将底层 socket 物理打碎
if (combinedSignal.aborted) {
  // 强行关闭连接，绝不残留僵尸保活
  response.body?.cancel();
}
```

通过这一层 `AbortSignal.any()` 缝合信号与主动 body 取消防御，我们不仅确保了用户能瞬间刹车，更从物理网络连接层面上防范了连接泄漏，为智能体底座的长期高可用运行筑起了防波堤。
