# 8.2 隐藏中间推理的工程艺术

在 8.1 节中，我们了解了 SSE 协议逐字推流的底层本质。一旦我们将大模型置于 ReAct 决策自循环（while-loop）中，智能体的大脑运作就会变得非常喧嚣：
1.  大模型生成 `Action`：`“我决定调用 read_file，参数是 path='notes.txt'”`。
2.  底座执行并返回 `Observation`：`“[文件内容]: 1. 整理季度架构总结...”`。
3.  大模型纠错、再次思考（Thought）并输出最终文本。

如果底座没有对推流管道进行精细控制，将大模型吐出的所有字节流无差别地推向前端：

*   **毁灭性的用户交互**：用户的屏幕上会突然闪过一连串的技术代码、JSON 结构和沙箱路径。这会让非技术用户感到极其迷惑和恐慌。
*   **重大的商业与安全风险**：智能体在后台调用的内部工具名称、参数结构与本地路径，会被前端抓包暴露。

本节我们将探讨如何在底座中建立**双轨管道过滤（Dual-Pipe Filtering）**，隐藏大脑内部调用的细节，只将优雅的执行进度与最终文本推送给用户。

---

## 一、 双轨管道过滤 (Dual-Pipe Filtering) 架构

为了在输出字符时“既有深度，又无噪音”，Freya 在事件总线层与大模型流式层建立起两条**绝对隔离的交互管道**：

```
                              ┌──> 系统事件通道 (EventBus) ──> tool:status 状态广播 (UI 进度条)
                              │
 [大模型 ReAct 决策流] ──> 【底座双轨分流机制】
                              │
                              └──> 用户流式通道 (SSE Stream) ──> 最终回答逐字推流 (User Only)
```

### 1. 系统事件通道 (EventBus 状态广播)
底座在内部执行 ReAct 决策循环时，当命中 `toolCalls` 并触发工具执行，通过 `eventBus.emit('tool:status', { sessionId, toolName, status: 'running' })` 向全系统广播生命周期状态。
前台 Web UI 或外部通道监听这些结构化 Event 流，将其转化为精美的人性化进度条（如显示一行微光动画：“*正在读取文件 notes.txt...*”），而不是直接显示 Raw JSON。

### 2. 用户流式通道 (协议级条件分流)
在 `plugins/plugin-openai/src/index.ts` 中，Freya 设计了极为精准的**流式条件分流开关**：

```typescript
// 摘自 plugins/plugin-openai/src/index.ts
const isStream = !!options?.onChunk && (!tools || tools.length === 0);
if (isStream) {
  requestBody.stream = true;
  requestBody.stream_options = { include_usage: true };
}
```

*   **决策与工具调用轮次**：由于携带了 `tools` 列表，系统不开启直接面向用户的流式传输，而是由内核完整接收结构化 Tool Call 并执行工具，通过 EventBus 发送进度事件。
*   **最终收敛回答轮次**：当大模型完成所有工具调用，进入无工具模式（`!tools || tools.length === 0`）输出最终答案时，底座才激活 `requestBody.stream = true`，逐字推流给前端用户，实现极致的 TTFT 体验。

## 二、 隐藏推理流 (Hidden Thinking) 的工程实现

现代前沿模型（如 DeepSeek-R1、OpenAI o1/o3）引入了专门的“深度思考流（Reasoning Content）”，在 API 返回中通过 `reasoning_content` 与正常的 `content` 分离返回。

然而，对于大多数不支持该特性的普通大模型，它们通常会将思考过程混在 `content` 中，并用特殊的 Markdown 标记包裹，例如：
`<thought> 我需要先查一下他的订单，再查他的工资... </thought> 您好，我已经为您查到了...`

底座必须能够在流式输出中，实时将 `<thought>...</thought>` 中的文本剥离并拦截，只把后半段推给用户。

## 三、 【避坑指南】防止被切碎的 XML 标签引发前端页面失控

在大模型推流时，字符是极度碎裂地返回的（比如一两个字符一两个字符地吐）。如果你试图用简单的 `string.includes('</thought>')` 来判断是否结束，会踩进一个**“标签跨 Chunk 被切碎”**的致命工程坑中。

### 1. 标签切碎泄露事故
假设大模型输出流在截断边界被切分为了两个连续 Chunk：
*   **Chunk A**：`“...正在查询订单。</th”`
*   **Chunk B**：`“ought> 您好，您的订单...”`

如果你只在接收到每个 Chunk 时用 `includes('</thought>')` 检测：
*   由于 Chunk A 只有 `</th`，未命中结束标签，底座判定仍处于思考区，将其拦截。
*   由于 Chunk B 只有 `ought>`，也未命中 `</thought>`，底座判定仍处于思考区，将其拦截。
*   **后果**：因为整个结束标示符被拦腰切断，底座**彻底迷失了状态**，导致大括号标签后的所有正常回答文本，全部被当成了思考过程进行拦截，前端用户永远收不到最终回答，智能体表现为“假死”。

### 2. 防御策略：流式状态机拦截器 (Streaming State Machine)
为了在流式中无损过滤思维流，底座必须引入一个**简单的状态机拦截器**。它不进行整串匹配，而是逐字进行字符探针状态转移：

```typescript
export class StreamingThinkingParser {
  private inThinking = false;
  private tagBuffer = "";
  
  // 状态机核心方法，接收逐字流，返回过滤后应该发送给用户的字符
  feed(char: string): string {
    // 1. 如果检测到可能是标签的开头
    if (char === '<') {
      this.tagBuffer = '<';
      return ""; // 暂扣，不发送
    }

    if (this.tagBuffer.startsWith('<')) {
      this.tagBuffer += char;
      
      // 检测是否命中了思考开始标签 <thought>
      if (this.tagBuffer === '<thought>') {
        this.inThinking = true;
        this.tagBuffer = "";
        return "";
      }
      
      // 检测是否命中了思考结束标签 </thought>
      if (this.tagBuffer === '</thought>') {
        this.inThinking = false;
        this.tagBuffer = "";
        return "";
      }

      // 如果缓冲区长度已经超出了标签的最大可能长度，说明不是合法标签，回滚释放
      if (this.tagBuffer.length > 10) {
        const fallback = this.tagBuffer;
        this.tagBuffer = "";
        return this.inThinking ? "" : fallback;
      }

      return ""; // 仍处于标签识别缓冲期
    }

    // 2. 正常字符路由
    return this.inThinking ? "" : char; // 若处于思考期，默默吞掉；否则安全输出
  }
}
```

通过这一层字符级状态机，无论大模型吐出的字节流有多碎，`</thought>` 标签在物理层面上被切得有多烂，底座都能在毫秒级内将其精准捕获并将其静默蒸发，保障了用户交互端的极致干净。

本节我们建立了双轨推流管道，并通过状态机隔离了大脑内部推理的喧嚣。在下一小节中，我们将实际切入 Freya 的消息通信总线，白盒剖析它是如何利用 EventEmitter 在整个底座广播这些状态事件的。
