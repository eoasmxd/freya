# 8.3 【白盒剖析】EventBus 事件广播与响应推送

在 8.2 节中，我们确立了双轨管道过滤（Dual-Pipe Filtering）的架构。底座拦截了用户可见的流式文本，将工具状态、计费更新、连接控制等一系列底层生命周期动作转化为结构化事件。

在 Node.js 的微内核插件式架构中，内核与插件、插件与插件之间是严禁采用强耦合的方法调用的（这违反了单向边界硬约束）。它们唯一的物理媒介，就是**事件总线（EventBus）**。

本节我们将实际白盒解剖 Freya 内核的事件总线实现（位于 `packages/core/src/event/event-bus.ts`），看懂它是如何基于 Node.js 原生 `EventEmitter` 进行二次包裹，并依靠**事件重播缓冲区（Replay Buffers）**优雅消灭“初始化竞争冲突”这一高难度硬核 Bug 的。

---

## 一、 FreyaEventBus：解耦核心与外部插件的物理媒介

在 `packages/core/src/event/event-bus.ts` 中，`FreyaEventBus` 实现了 SDK 中的 `EventBus` 抽象接口。

它内部包裹了 Node.js 原生的 `EventEmitter`：

```typescript
import type { EventBus } from '@eoasmxd/freya-sdk';
import { EventEmitter } from 'node:events';

export class FreyaEventBus implements EventBus {
  // 1. 物理包裹原生 EventEmitter 实例
  private emitter = new EventEmitter();

  // 2. 事件重播历史缓冲区
  private replayBuffers = new Map<string, any[][]>();
}
```

### 为什么不直接用 `new EventEmitter()` 传给插件？
*   **接口隔离原则**：如果直接给外部插件透传 Node 原生的 `EventEmitter`，插件就有权调用诸如 `removeAllListeners()` 这种极具破坏性的全局方法，瞬间瘫痪整个系统的事件广播线。
*   **物理契约约束**：通过 `EventBus` 接口进行包裹隔离，底座仅暴露了安全的 `on`、`off` 和 `emit` 三个原子契约，锁死了外界篡改内核监听线的后门。

---

## 二、 解决初始化顺序冲突：事件重播缓冲区 (Event Replay)

在微内核（Microkernel）与 Monorepo 插件加载体系中，我们会面临一个经典的**时序初始化大坑**：

### 1. 物理时序竞争冲突 (Race Condition)
系统在启动时，会扫描 `plugins/` 目录加载插件。
假设**插件 A（LLM 计费模块）**最先被加载，它在初始化完成的瞬间，向总线 `emit('init:billing', { rate: 0.1 })` 广播了计费参数。
然而，负责接收这些计费参数并显示在 UI 上的**插件 B（WebSockets 通道模块）**在 50 毫秒后才被加载就绪，随后调用了 `on('init:billing', ...)`。
*   **灾难下场**：因为插件 B 的监听器注册晚了 50 毫秒，大牌子广播已经播放完毕。插件 B 彻底漏掉了这笔初始化参数，导致前台 UI 的计费面板显示为空白，发生状态不一致 Bug。

### 2. 救赎：Freya 的重播缓冲区设计
`FreyaEventBus` 通过在 `emit` 和 `on` 之间插入一个 **Replay Buffer 历史缓存区**，物理消灭了这一时序冲突：

```typescript
emit(event: string, ...args: any[]): void {
  // 1. 正常广播当前活跃的监听器
  this.emitter.emit(event, ...args);

  // 2. 💡 物理过滤：只将含有 'register' 或 'init' 的系统根源事件存入缓冲区
  const shouldBuffer = event.includes('register') || event.includes('init');
  if (shouldBuffer) {
    if (!this.replayBuffers.has(event)) {
      this.replayBuffers.set(event, []);
    }
    // 将该事件的历史参数追加存盘
    this.replayBuffers.get(event)!.push(args);
  }
}
```

当任何插件在**未来较晚的某个时序点**调用 `on()` 注册监听时，重播防线会瞬间苏醒：

```typescript
on(event: string, listener: (...args: any[]) => void): void {
  // 1. 注册正常的常规事件监听
  this.emitter.on(event, listener);

  // 2. 💡 历史追溯：检测该事件名是否在 replay 缓冲区中有未读历史
  const buffer = this.replayBuffers.get(event);
  if (buffer) {
    for (const args of buffer) {
      // 3. 巧妙妙用 Node.js 的 setImmediate，将重播操作丢入事件循环的下一个 Tick 异步执行
      // 绝对防止同步阻塞当前注册过程，消灭死锁
      setImmediate(() => {
        listener(...args); // 依次将遗漏的历史事件强行“塞”给新监听器
      });
    }
  }
}
```

## 三、 setImmediate 的工程妙用

在重播机制中，为什么不能直接同步调用 `listener(...args)`，而要用 `setImmediate` 包裹？

如果在 `on()` 中直接同步循环执行 `listener()`：
*   如果监听器内部又触发了其他连锁 `emit` 动作，会导致当前 `on()` 调用栈（Call Stack）陷入恐怖的**同步递归回环**。
*   这会发生 CPU 100% 爆满，或者因为超出 V8 最大调用栈深度直接报 `Maximum call stack size exceeded` 报错死机。
*   **物理本质**：通过 `setImmediate`，底座告诉 Node.js：“先把当前的 `on` 注册完并释放控制流，在下一个 Tick（微步）里再去异步重播刚才的历史”。这在物理时序上实现了最安全的协程避让，保障了系统的极度平稳。
