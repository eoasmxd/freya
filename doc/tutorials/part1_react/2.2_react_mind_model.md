# 2.2 ReAct 心智模型与推演

在 2.1 节中，我们确立了智能体（Agent）区别于普通聊天机器人（Chatbot）的核心在于其具备“自主的循环控制流”。那么，在具体的工程实现中，我们该如何教导大模型在每一次“接龙”时进行有逻辑的思考、决定调用什么工具，并正确阅读工具返回的数据呢？

目前行业内最经典、应用最广泛的心智骨架，就是由谷歌和普林斯顿大学于 2022 年提出的 **ReAct（Reasoning & Acting）心智模型**。

本节我们将深入解剖 ReAct 决策环的物理机制、剖析其底层的 Prompt 模板结构，并探讨如何通过健壮的解析器防范大模型格式失控。

---

## 一、 为什么需要 ReAct？CoT 与单纯 Acting 的双重缺陷

在 ReAct 诞生之前，学术界和工业界在提升大模型能力时，分别走向了两个极端：

### 1. 思维链（CoT, Chain of Thought）的缺陷
思维链技术通过在 Prompt 中加入“让我们一步步思考（Let's think step by step）”，引导模型在输出最终答案前写下中间的推理步骤。
*   **物理缺陷**：CoT 依然是一个**“闭门造车”**的过程。大模型只能基于已有的静态训练权重进行逻辑联想。如果它缺乏实时数据，或者在中间某一步发生了逻辑偏差（Hallucination），它无法通过任何外部物理手段纠正自己，只能顺着错误的思路一路狂奔。

### 2. 单纯行动（Acting-Only）的缺陷
另一种方案是直接给大模型挂载工具，一句话让它调用 API（如早期的插件系统）。
*   **物理缺陷**：单纯的 Acting 缺乏**“反思能力”**。大模型直接面对各种零乱的 API 响应，一旦接口报错或返回了不符合预期的数据，模型大脑没有一个“思考缓冲带”去重新分析，往往会直接抛出逻辑异常，或者在多次调用间迷失方向。

### 3. ReAct：Reasoning 与 Acting 的交织交响
ReAct 完美地将 **Reasoning（逻辑推理）** 与 **Acting（物理行动）** 编织在同一个自循环中：
*   **推理（Reasoning）**：帮助模型规划步骤、跟踪状态、分析异常、自我修正。
*   **行动（Acting）**：帮助模型走出静态参数的局限，从真实的物理世界获取客观事实（Observation）。

## 二、 ReAct 的经典推演时序

让我们用一个具体任务来看看 ReAct 在底座中的多轮运行轨迹。
*   **任务目标**：查询小明（ID: 101）的薪资，并判断是否超过公司合规线（$10,000$ 元）。

```
[第一轮循环]
  ├─ Thought (思考): 用户想知道小明的薪资是否超标。我需要先获取小明的薪资数据。我应该调用 get_salary 工具。
  ├─ Action (行动): 调用工具 get_salary(userId=101)
  └─ Observation (观察): [底座带回结果]: 12000

[第二轮循环]
  ├─ Thought (思考): 刚才的工具返回了小明的薪资是 12000 元。12000 大于合规线 10000 元。小明的薪资已经超标了。
  ├─ Action (行动): 无需再调用工具。
  └─ Final Answer (最终回答): 小明（ID: 101）的当前薪资为 12,000 元，已超出 10,000 元的合规线，处于不合规状态。
```

在这轮交替中，每一次的 `Thought` 都充当了大脑的**状态寄存器**，它读取上一步的 `Observation`（事实），更新当下的计划，再吐出下一个 `Action`（动作）。

## 三、 ReAct 的物理 Prompt 模板剖析

大模型并不会自发理解 `Thought`、`Action` 和 `Observation` 的游戏规则。底座系统必须在 System Prompt 中为它树立起严格的“语法高地”。

以下是一个经典的、不依赖大厂原生 Function Calling 能力（即纯文本模式下）的 ReAct 模板结构：

```markdown
# 角色与约束
你是一个具备工具调用能力的智能体。对于用户的目标，你必须以交替“思考-行动-观察”的闭环步骤来逐步完成。

# 语法格式要求
在每一步交互中，你只能输出以 `Thought:` 和 `Action:` 开头的两段文本。禁止输出多余内容。
请严格遵循以下语法格式：

Thought: 仔细思考你当前所处的状态，分析你还需要什么数据，以及下一步该做什么。
Action: 选择一个可用的工具调用，格式为: tool_name(arguments)
Observation: 此处不要由你输出！这是系统底座在执行工具后带回的数据。

当你确认任务已经彻底完成时，请使用以下格式输出：
Final Answer: 给出你的最终完整结论。

# 可用工具列表
1. get_salary(userId: number) -> 返回该用户的月薪（数值）。
2. send_alert_email(email: string, message: string) -> 发送警告邮件。
```

在底层运行中，大模型接龙输出到 `Action: get_salary(userId=101)` 时，底座执行器会在检测到特定换行符后**强行切断 LLM 的生成流**（强制中断接龙）。然后把运行 get_salary 得到的返回值拼接到文本的末尾：`\nObservation: 12000\n`。最后，再次唤醒大模型开始接龙。

## 四、 【调试与避坑】格式失控与 Parser（解析器）的鲁棒性防御

在工程开发中，ReAct 最脆弱的一环往往就是**解析器（Parser）的健壮性**。

虽然学术界和早期框架常用正则表达式去解析文本中的 `Action: tool_name(args)`，但**在 Freya 内核中，我们实际采用的是大模型原生的 Function Calling（结构化工具调用）机制**。大模型会输出结构化的 `toolCalls` 数据（包含工具名与 JSON 格式的参数字符串）。

然而，即使使用原生 Function Calling，小参数量模型在长上下文下依然可能输出损坏的 JSON。这就需要解析器具备鲁棒的防线。

### 1. 典型的“参数解析失控”标本：
*   **标本 A (损坏的 JSON)**：`{userId: 101}`（键名没有被双引号包裹，不符合标准 JSON 规范）。
*   **标本 B (截断的 JSON)**：`{"userId": 10`（由于 Token 限制或模型提前停止导致 JSON 截断）。
*   **标本 C (自作聪明的嵌套)**：`{"arguments": "{\"userId\": 101}"}`（模型额外嵌套了一层转义）。

### 2. 调试实战：Freya 内核的 JSON 容错与错误回流引导

为了防止 Agent 系统因参数格式抖动崩溃，Freya 在内核中采用了以下双重防线：

#### 防线一：内核的 JSON 异常安全捕获
在执行工具参数解析时，绝不能让解析异常直接向外抛出导致整个 Executor 崩溃。内核会在捕获 JSON 解析错误后，优雅地降级并生成错误日志。

与 Freya 内核中一致的参数解析防守代码如下：

```typescript
let args: any;
try {
  // 💡 尝试解析模型返回的结构化工具参数
  args = JSON.parse(toolCall.arguments);
} catch (parseErr: any) {
  // 记录错误日志，并阻止异常向上击穿
  logger.error(`[FreyaAgentExecutor] 解析工具参数失败: ${toolCall.arguments}`, parseErr);

  // 触发工具执行状态为失败
  eventBus.emit('tool:status', {
    sessionId,
    toolCallId: toolCall.id,
    toolName: toolCall.name,
    status: 'failed',
    result: `JSON 解析失败: ${parseErr.message}`
  });

  // 降级返回标准的错误反馈结构
  return {
    role: 'tool',
    content: `Error during JSON parsing: ${parseErr.message}`,
    toolCallId: toolCall.id,
    toolName: toolCall.name
  };
}
```

#### 防线二：错误反馈引导机制（Error Feedback Loop）
当上述解析捕获失败并返回 `Error during JSON parsing` 后，该错误内容会作为标准的 `tool` 角色消息（即 Observation 反馈）重新灌回大模型的上下文。

大模型在下一轮决策（Thought）中，会读到这一解析失败的物理反馈，意识到自己上一轮输出的参数有误，并在接龙中自动纠正格式重新生成。这种将格式错误“回流水管”的设计，是保证智能体系统在线上高并发环境中自我愈合的核心工程秘诀。
